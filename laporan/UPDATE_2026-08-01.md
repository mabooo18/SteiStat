# Update Log — Sketch Restructuring, Dummy-Cell Verification, and Python UI Fixes (2026-08-01)

This session covered three things in sequence: getting the newly reorganized firmware (`Software/update 2 (18 Juli 26)/AD5941_25/`) to compile at all, running a live dummy-cell test across CA/CV/SWV/DPV once it did, and then root-causing two distinct problems the dummy-cell test surfaced in the Python test UI. It is a direct continuation of `TECHNICAL_REPORT_EN.md` §10 and `ARCHITECTURE_DOCUMENT.md` §8 (2026-07-18 session) — this document uses the same before/after format and cross-references those sections rather than repeating their content.

## 1. Context: A New Folder, A New Compile Error

The project gained a new top-level location, `Software/update 2 (18 Juli 26)/AD5941_25/`, sitting alongside (not replacing) the original `Software/AD5941_25/` tree the earlier reports were written against. Two files in the new location hadn't been updated for their new position, and a second, older sketch (`HunStat2.ino`) had been placed in the same folder as the current one — a combination that broke compilation outright.

### 1.1. `HunStat2.ino` — Stale Relative Include Paths

**Symptom**: `arduino-cli`/Arduino IDE compilation failed immediately with:
```
HunStat2.ino:38:10: fatal error: ../src/setup/ad5941_setup.h: No such file or directory
```

**Root cause**: Before this reorganization, `HunStat2.ino` lived one directory *below* the shared `src/` folder (visible in git history as `HunStat2.ino/HunStat2.ino.ino`), so `#include "../src/setup/ad5941_setup.h"` correctly walked up one level to find it. The reorganization moved `HunStat2.ino` to sit directly *beside* `src/` (both now children of `AD5941_25/`), but its `#include` lines still carried the old `../` prefix — now pointing one level too high, into a folder with no `src/` at all. The sibling `AD5941_25.ino` in the same folder already used the correct un-prefixed form (`#include "src/setup/ad5941_setup.h"`), confirming the diagnosis by direct comparison.

**Fix**: Removed the leading `../` from all 8 local `#include` lines in `HunStat2.ino` (lines 38–49): `src/setup/ad5941_setup.h`, `src/data_storage/data_storage.h`, `src/communication/communication.h`, `src/electrochemical_methods/c_eis.h`, `ad5940.h`, `AD5940.h`, `utilities.h`, `src/ad5940/debug.h`.

### 1.2. Two Competing Sketches in One Folder

**Symptom**: Fixing §1.1 would have immediately surfaced a second, worse failure — mass "redefinition" errors — because Arduino compiles every `.ino` file in a sketch folder as one combined program.

**Root cause**: `AD5941_25.ino` (the current, actively developed sketch) and `HunStat2.ino` (an older, largely monolithic variant of the same firmware — the same one the `command_processing.cpp` dead-code path in `ARCHITECTURE_DOCUMENT.md` §3.4 was written against) were sitting in the same `AD5941_25/` folder. A direct comparison of top-level function definitions in both files found **~20 identical names in both**, including `setup()`, `loop()`, `eisScan()`, `CalculateOCP()`, `Config_LPLOOP()`, `Calibrate_HSDAC()`, `ConfigureHSLoopCfg()`, and more — these are two independent, complete alternate firmware images, not complementary files.

Cross-checked and confirmed *not* a conflict: the root-level helper files (`XIAOPort.cpp`, `cv.cpp`, `utilities.cpp`, the `ad5940.h`/`AD5940.h` wrapper) are genuinely shared infrastructure both sketches need — `src/ad5940/ad5940.cpp` and `src/setup/ad5941_setup.cpp` only *call* functions like `AD5940_CsClr()`, `Log()`, and `cvSetup()` (declared `extern`), they never redefine them. Only the two `.ino` files themselves collide.

**Fix**: Moved `HunStat2.ino` out to its own sibling sketch folder, `Software/update 2 (18 Juli 26)/HunStat2/HunStat2.ino`, so `AD5941_25/` now contains exactly one `.ino` file matching its folder name (the standard Arduino sketch convention).

**Known follow-up (not fixed, by design)**: `HunStat2.ino` in its new location no longer has access to `src/` or the other shared root files it depends on (it was moved, not duplicated-with-dependencies). It will not compile standalone as-is; it would need its own copy of the shared infrastructure, or to be pointed back at the `AD5941_25/` tree via includes, if it needs to be built again in the future.

## 2. Dummy-Cell Hardware Verification

With the sketch compiling and uploading again, the Python test console (`python_ui/hunstat2_test_ui.py`) was run against a physical **3-branch dummy test cell** (see `hasil/dummy cell.png`) in place of a real electrochemical sample, to sanity-check CA/CV/SWV/DPV output shapes before trusting the board on real samples. The dummy cell exposes three independently-wired branches off a shared CE/RE node:

| Branch | Components | Expected electrical behavior |
|---|---|---|
| **we-A** | Anti-parallel diode pair (D1/D2, BAS16) ‖ C1 (33 nF), + R1 (560 Ω) | The only nonlinear branch — should produce a genuine peak/threshold-shaped voltammetric response, the closest analog to a real redox reaction on this board. |
| **we-B** | R2 (10 kΩ, 0.1%) only | Purely ohmic — differential current is bias-independent, so SWV/DPV here should be flat (± noise), never peaked. |
| **we-C** | R3 (10 kΩ) ‖ C2 (33 nF), + R4 (560 Ω) | RC time constant ≈ 330 µs — far faster than any practical CA sample interval, so CA here should look flat from the very first sample; no visible decay is physically possible at normal sampling rates. |

**Observed** (`hasil/CA.png`, `SWV.png`, `DPV.png`, `CV.png`): CA and SWV both plotted as noisy, shapeless scatter with no discernible decay or peak; DPV plotted with a large spurious diagonal line cutting across an otherwise-plausible dataset; CV logged exactly 2 data points on every run regardless of configured Start/Stop/Step. None of these matched the "textbook" shapes in `TECHNICAL_REPORT_EN.md` §8.

Two of these four observations turned out to be genuine software bugs (§3 below, both fixed). The other two are addressed here since they were raised during this session but are **not fixed** — they are either expected physics or an open hardware-routing question:

* **CA's flat, noisy trace is expected if it was measuring the we-C branch** — a 330 µs RC time constant against a typical 20 Hz (50 ms) CA sample rate means the capacitor has already fully settled ~150× over before the very first sample is taken. No firmware change can make a decay curve visible at that sample rate on that branch; a much smaller R×C dummy branch or a much faster CA sample rate would be needed to actually observe one.
* **SWV/CA's lack of any peak may indicate the wrong branch is being sensed, not a firmware bug** — `C_CA::ConfigDCMeasurement()`, `C_SWV::ConfigDCMeasurement()`, and `C_DPV::ConfigDCMeasurement()` all hardcode `HpLoopCfg.SWMatCfg.Nswitch = SWN_SE0` (see `ELECTROCHEMICAL_METHODS_EXPLANATION.md` §2.1 and `ARCHITECTURE_DOCUMENT.md` §3.4). There is currently **no electrode-channel-selection mechanism anywhere in the firmware** — every method always senses through the same fixed `SE0` input, regardless of which physical `we-A`/`we-B`/`we-C` pin the operator intended to test. If `SE0` is not the pin physically wired to the diode branch (`we-A` — the only branch that can produce a peak), a flat/noisy trace is exactly what would result, correctly, from measuring `we-B` or `we-C` instead. **Open item**: confirm on the physical board which `we-X` pin `SE0` is wired to; if it isn't `we-A`, either rewire, or add a serial-selectable channel mux to the firmware (see §5 Recommendations).

## 3. Python UI Bugs Found and Fixed

### 3.1. CV Stuck at Exactly 2 Data Points — Unit Mismatch (Volts vs. Millivolts)

**Symptom**: Every CV run, regardless of the configured Start/Stop/Step/Scan/Cycle values, produced exactly 2 data points and rendered as a straight 2-point line (`hasil/CV.png`).

**Root cause**: `RampTest.h` and `rampTest.cpp` work entirely in millivolts throughout — `DAC12BITVOLT_1LSB` is defined as `2200.0f / 4095 ≈ 0.537 mV`, and the step-count formula in `AppRAMPSeqInitGen()` (`rampTest.cpp:732`, reached via the live `communication.cpp` → `cvSetup()` → `_AD5940RampStructInit()` → `AppRAMPInit()` call chain) computes:
```cpp
StepNumber = (uint32_t)(fabsf(RampPeakVolt1 - RampPeakVolt2) / (DACCodePerStep * DAC12BITVOLT_1LSB)) * 2;
```
The Python UI's CV panel, however, defaults its Start/Stop/Step/Scan fields to **volt-scale** decimal values — `0.5`, `-0.22`, `0.002`, `0.8` — unlike every other method's fields (CA/SWV/DPV), which are already millivolt-scale integers (`100`, `1400`, `25`, …). `_apply_selected_method_params()` sent these values through to the firmware completely unconverted. The firmware then saw a `0.72` "mV" total swing instead of the intended `720 mV`:
```
StepNumber = |0.5 − (−0.22)| / (1 × 0.537) × 2 ≈ 2.68 → truncated to 2
```
— which is exactly the "2 points, every time" symptom. (`Estep = 0.002` "mV" is also below one DAC LSB, so `DACCodePerStep` additionally clamps to its 1-LSB minimum — a secondary effect of the same root unit error.) Confirmed this bug lives on the currently-active code path: `communication.cpp` (the live parser, per `AD5941_25.ino`'s `loop()` → `g_Comm.ReadAndProcess()`) contains the identical `sscanf(token, "D %f,%f,%f,%f,%i", ...)` pattern feeding the same shared `cvSetup()` in `cv.cpp` — the dead `command_processing.cpp` copy has the same pattern too, but is unreachable either way (`ARCHITECTURE_DOCUMENT.md` §3.4).

**Fix**: `hunstat2_test_ui.py`'s `_apply_selected_method_params()`, CV branch, now multiplies Start/Stop/Step/Scan by `1000.0` before building the `D <start_mV>,<stop_mV>,<step_mV>,<scan_mV_s>,<cycle>` command string, converting the UI's volt/‑per‑second fields to the millivolt/‑per‑second units the firmware expects. Field labels were also updated from `Start/Stop` / `Step/Scan/Cycle` to `Start/Stop (V)` / `Step(V)/Scan(V/s)/Cycle` so the unit is explicit rather than implicit. With the fix, the same default parameters (`0.5 V → −0.22 V`, `2 mV` step, `0.8 V/s` scan) now compute a step count of roughly **720** — a normal, full-resolution CV sweep instead of a 2-point stub.

### 3.2. DPV Plot Showed a Spurious Diagonal Line

**Symptom**: The DPV plot (`hasil/DPV.png`) showed a large, steep diagonal line cutting from the top of the plot down to the baseline over roughly the first 15–20% of the x-axis, then a plausible-looking noisy trace for the remainder.

**Root cause**: `_redraw_plot()` in `hunstat2_test_ui.py` connects consecutive points in **arrival order** (the order they were appended to `mode_points[mode]`), not sorted by x-value/voltage. Separately, `_run_selected_method()` never cleared `data_points`/`mode_points` before starting a new run — only the manual "Clear" button did. So running DPV more than once without pressing "Clear" in between caused the second run's points to be appended directly after the first run's, and the plot then drew a line from the *first* run's last point (near the end of its voltage range) straight to the *second* run's first point (back near the start) — exactly the long diagonal artifact observed. The underlying DPV measurement data itself was not corrupted; this was purely a plot-continuity bug in the desktop UI.

**Fix**: Added a `_clear_mode_data(mode)` helper (removes that method's entries from both `data_points` and `mode_points`, then refreshes the summary counter) and call it automatically from `_run_selected_method()` immediately before sending the run-trigger command for the selected method. Every "Run Selected" now starts that method's plot from a clean slate without requiring a manual "Clear" click first.

## 5. Recommendations / Open Items Raised This Session

1. **Confirm the `SE0` → physical `we-X` pin mapping on the board**, and/or add a serial-selectable working-electrode channel mux to the firmware. Without one, CA/SWV/DPV can only ever sense whichever single dummy-cell branch (or real electrode) happens to be wired to `SE0` — see §2. This is the most likely explanation for the still-unresolved flat/noisy CA and SWV traces.
2. **Re-run the dummy-cell CA/SWV/DPV/CV test after confirming §5.1**, ideally with the diode branch (`we-A`) explicitly connected to whatever pin `SE0` maps to, to get a clean baseline "known good" reference plot set for future regression comparison.
3. **Give every parameter-entry field in the Python UI an explicit unit in its label** (the CV panel was the one instance found this session where the UI's implied unit silently disagreed with the firmware's — see §3.1's before/after on the CA/SWV/DPV panels, which were already unambiguous). A brief audit of the remaining panels (EIS, OCP) for the same class of mismatch would be cheap insurance.
4. Carry forward the still-open items from the 2026-07-18 session (`ARCHITECTURE_DOCUMENT.md` §8, items 6–7): the status LED color table not actually reflecting on hardware, and the dead `command_processing.cpp`/free-function `electrochemical_methods.cpp` duplicate still compiling alongside the live class-based path.
