# OOP Analysis — SteiStat / AD5941_25 Firmware

**Method:** every `.h`/`.cpp` file under `AD5941_25/src/` was read in full. A repo-wide search for `virtual`, `: public` (inheritance), `override`, and `template<` returned **zero matches** in project code (only present, if at all, inside the vendor AD5940 driver — which itself has none either). This single fact governs the whole assessment below: whatever encapsulation exists, there is no inheritance, no polymorphism, and no interface abstraction anywhere in the codebase.

## Duplication Summary (separate from the per-file table because it crosses files)

The codebase ships **two parallel implementations** of the same functionality in two places:

1. **CA/SWV/DPV**: class-based (`C_CA`, `C_SWV`, `C_DPV`, bound to `C_DataStorage`) *and* free-function (`electrochemical_methods.cpp`, bound to its own separate globals), with identical register-configuration code and magic numbers copy-pasted three times within the class versions alone.
2. **Command processing**: class-based (`C_Communication`, ~622 lines) *and* free-function (`command_processing.cpp`, ~704 lines), each independently implementing the same ASCII command grammar against disjoint sets of global variables.

Both duplications matter for the paper: they are direct evidence against an "OOP refactor" narrative, and they are a correctness risk (two code paths can diverge on the same nominal parameter).

## Overall Verdict: **Partially OOP** (weak end of "partial")

Justification, in order of weight:

1. **No inheritance, polymorphism, or interfaces anywhere in project code.** Five electrochemical-method classes (`C_CA`, `C_DPV`, `C_SWV`, `C_EIS`, `C_OCP`) are a textbook case for a common `IElectrochemicalMethod` base with a virtual `Run()` — none exists. `C_CA::ConfigDCMeasurement()`, `C_DPV::ConfigDCMeasurement()`, and `C_SWV::ConfigDCMeasurement()` are verbatim-identical instead of being one shared base method.
2. **The central "class," `C_DataStorage`, has 100% public fields and a single trivial method.** Its own source comment states its purpose is to replace `extern` globals with one shared object — a relocation of global state, not encapsulation. Every method class reaches directly into its public fields.
3. **Every method class is directly coupled to the vendor register-driver API and to Arduino runtime calls (`Serial`, `digitalWrite`, `delay`) inside the same functions that do unit conversion and protocol framing.** There is no hardware-abstraction-layer interface standing between "measurement logic" and "register access" — which is the opposite of what an "OOP potentiostat" claim would need to demonstrate.
4. **Two full parallel implementations of the command layer and of CA/SWV/DPV exist simultaneously** (class-based vs. free-function), indicating the OOP layer was added alongside, not integrated into, the original procedural firmware.
5. **Genuine encapsulation exists only in two places**: `C_Communication` (private history buffer, real invariant it manages) and `C_AD5941_Setup` (private NeoPixel object, though leaked via a raw-pointer getter). The other six classes use `class` as a grouping syntax indistinguishable from a namespace.

### What this means for the paper

The manuscript **cannot** honestly claim "strong OOP architecture," "polymorphic method dispatch," or "clean hardware abstraction layer" as currently implemented. It *can* honestly claim: a partial migration from procedural/global-variable C toward C++ classes, with identified concrete next steps (Phase 3 architecture) to complete that migration — e.g., a shared base class for electrochemical methods, a real HAL boundary, and removal of the duplicate free-function code paths. Positioning the paper's contribution around "we diagnose the current architecture and propose/implement a completed OOP refactor" is defensible from the evidence; claiming the *current* code is already a mature OOP design is not.
